# Map: Exact copy v2

Label: wayfinder:map

## Destination

A locked spec for the fingerprint, the export set format, import, the health check and the discrepancy report. The spec can then be split into build tickets that deliver a verified, exact copy of a source datafile into a target datafile, quickly.

## Notes

- Domain: 4D v21 component. See [GLOSSARY.md](../../../GLOSSARY.md) for terms and [README.md](../../../README.md) for the current behaviour and the known verification gaps.
- Skills: `grilling` and `domain-modeling` for grilling tickets. `research` for research tickets. Follow `CLAUDE.md` (YAGNI, 31-character limit on method names).
- Plan, don't do. No production code changes inside this map, except task tickets that only exist to unblock a decision.
- Prefer 4D classes where they fit (set 2026-10-01 in [Define the shared API](issues/12-define-shared-api.md)). Shared methods stay as the host's entry points.
- Settled at charting (2026-09-30):
  - **Equality:** every stored field value must be equal, and a null value counts as equal to a blank one. Line endings are significant. Each table's record count and sequence number must match. Record numbers are excluded.
  - **Structure:** if the source and target structures differ, the tool refuses to run.
  - **Discrepancy report:** field-level detail (missing, extra, or changed records, identified by record key, with the changed fields named).
  - **Comparison:** runs automatically after import, and is also available as its own `Compare` shared method.
  - **Record key:** every exported table must have a unique, non-null primary key. The health check flags any table that doesn't, and export refuses it.
  - **No compatibility:** old XML exports and old MD5 checksum files are not supported. Legacy XML import code can be deleted.
  - **Scale:** datafiles are 30–40 GB, run standalone on a copy. Faster is better.
  - **Minimum version:** 4D v21.
  - **Health check:** keep it, and consider new checks.
  - **Benchmarking:** a generated datafile for repeatable benchmarks, and a real customer copy for a final check.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [Review current hashing, export, format and import](issues/01-review-current-implementation.md): the current fingerprint never hashes the last record of each block, and its text encoding collides (delimiter injection, line endings folded, objects flattened). Reals and Int64 go through `String()`. The export set has no manifest, sequence number or structure signature. The JSON importer is unwired and ignores `save()` failures. Each table is read about 4 times. [Findings](research/01-review-current-implementation.md)
- [Survey 4D v21 options for fast, exact hashing and bulk read/write](issues/02-survey-v21-hashing-and-bulk-io.md): `Generate digest` (MD5/SHA-1/SHA-256/SHA-512) hashes only whole values and is thread-safe. JSON and `String()` lose data (pictures, 13-digit reals, Int64 read as Real, line endings on text writes), while byte routes (`VARIABLE TO BLOB`, `writeBlob`, `SEND RECORD`) stay exact. Setting the sequence number must run cooperatively. SQL can disable indexes, constraints and triggers in bulk. No primary source gives speed numbers, so the benchmark task has to supply them. [Findings](research/02-survey-v21-hashing-and-bulk-io.md)
- [Build a generated benchmark datafile and a baseline timing](issues/03-benchmark-datafile-and-baseline.md): `__Bench_Generate(scale)` builds a repeatable datafile (1.0 ≈ 5.7 GB). Compiled baseline on an M1 Max with 10 cores: the serial export takes 74 min and the checksum 6 min. Export cost follows record and field count, not bytes, and compiling barely changes it. Ten workers give only 1.6× (50 min), because the largest table is 94% of the wall-clock time. [Results](research/03-baseline-compiled.json)
- [Define the fingerprint](issues/04-define-fingerprint.md): SHA-256 over one canonical byte buffer per record. The fields go in field-number order, fixed-width values raw, variable-width values with a 4-byte length prefix, and no tags. Null encodes as blank, including a null object as `{}`. Reals are bit-exact. Pictures and objects are hashed as their `VARIABLE TO BLOB` bytes, and BLOBs as stored. There is no table-level fingerprint. Int64 beyond ±2^53, Float fields and unreadable subtable fields are not encoded and go to the health check.
- [Define the export set format](issues/05-define-export-set-format.md): each record is stored as its fingerprint buffer, byte for byte, with a 4-byte length prefix, in record-key order and uncompressed. Segments of up to 100 MB are named by the position of their first record and sit in one folder per table. A `manifest.json`, written last, holds the run, the source identity, a whole-structure signature, each table's counts, sequence number and field list, and each segment's SHA-256. A failed export is rerun from scratch.
- [Decide where fingerprints are computed and stored](issues/06-fingerprint-compute-and-storage.md): nothing is stored. The export set is the source's fingerprint plus its values. `Compare` always checks an export set against the current datafile: it re-reads the target in record-key order, streams the segments beside it, hashes both buffers, and slices them by field when they differ. The import flushes the cache and then runs `Compare` in the same session. Each segment's SHA-256 is checked first, so a damaged segment is reported as damage to the export set, not as discrepancies.
- [Import strategy](issues/07-import-strategy.md): it runs in 4D local mode only, takes the export set's path, and checks the manifest, version, structure signature, source identity and every segment's SHA-256 before writing anything. It then disables triggers and constraints, closes any open log file, and gives one table per worker, largest first: truncate, `PAUSE INDEXES`, classic `CREATE`/`SAVE RECORD` one segment at a time, `RESUME INDEXES`. The sequence numbers (selector 31) are set last and cooperatively, then it re-enables, runs `FLUSH CACHE` and `Compare`. No transactions. Any failure stops the run and marks the target unusable.
- [Comparison and discrepancy report](issues/08-comparison-and-discrepancy-report.md): `Compare_ExportSet(path; options)` merges each table on the record key in lockstep. Keys match byte for byte, the target's `<` decides missing or extra, and an order guard catches a collation mismatch. The kinds are missing, extra, changed (with both values), duplicate, record count and sequence number. A damaged segment, an order break or an unreadable record leaves only its key range unverified. Detail is capped at 1,000 records per table. The verdicts are exact, notExact, inconclusive, refused and failed. Each run writes a .txt and .json pair into the export set. The import calls Compare last and succeeds only on exact.
- [Health checks](issues/09-health-checks.md): there are blockers (what Compare can't see, plus the record key) and signs of damage. The export runs the blocker gate itself, first, every time, with no override. The gate checks for a primary key (empty tables are exempt), keys that are unique under 4D's comparison and not blank or an all-`0x20` UUID, no Float or unreadable subtable fields, no Int64 beyond ±2^53, and no null Auto UUID. The standalone run also scans for bad characters (now including U+FFFF and unpaired surrogates), which it only reports. The fixer stays, but runs only when the gate passes. Write-side checks and `VERIFY DATA FILE` are dropped. The report is a `Health check …txt/.json` pair with the verdicts passed, warnings, blocked and failed.
- [Split large tables across workers](issues/10-split-large-tables-across-workers.md): yes, in the scan, the fixer, export, import and Compare, built in the first round with no measurement first. A table gets jobs by its fair share of records × fields, with at least 50,000 records per job, and each job is a key range. Source-side jobs query their range and check its count. The manifest gains each segment's `first_key` and `last_key`, which Compare uses for job ranges, an order pre-check and exact damaged ranges. Import truncates and pauses every table first, then loads, then resumes indexes per table. Jobs never show in reports.
- [Dialog for a guided export and import](issues/11-guided-dialog.md): a step list (Health check, Export, Switch to target, Import, Compare) replaces the tabs. The dialog stays open while a cooperative coordinator runs the job, and progress arrives by `CALL FORM`: a phase line, a phase bar with an ETA, and a table grid. 4D Progress and the IH_Log window go. It stores no state: it finds export sets in the data folder, and its marks come from a report pair that every pass now writes, recording its datafile. Pre-flight runs each pass's own checks. The manifest gains the data language, and import and Compare refuse a mismatch. Switch to target calls `CREATE DATA FILE` in the same folder. Stop takes each pass's failure path. Banners show the result's own next-step text and the tables left out. [Facts](research/11-dialog-4d-facts.md)
- [Define the shared API](issues/12-define-shared-api.md): the six shared methods stay backward compatible, as one-line wrappers that still return a path, because downstream hosts call them. `Compare_ExportSet` is the only new one. Five pass classes (`HealthCheckPass`, `FixerPass`, `ExportPass`, `ImportPass`, `ComparePass`) are exposed in the `ExportImport` namespace with `check()` and `run()`, and everything else has a `_` prefix. Every `run()` returns one result envelope, with the verdict and next-step text, and runs only in local mode. The dialog attaches a window and a shared stop flag. Jobs are `_` classes run by `CALL WORKER` with a Formula. The XML, JSON and MD5 code goes after the bench moves to the new API. [Facts](research/12-classes-4d-facts.md)
- [Logging and report contents](issues/13-logging-and-report-contents.md): every run writes a run report (`.txt` and `.json`) and a run log (`.log`) with the same name. The run report is written at the start as `interrupted`, rewritten on each phase change with that phase's next step, and written again at the end, so a crash leaves evidence. The `.txt` layout is shared, with `<Pass>: <verdict>` on line 1 and counts only. The envelope gains `phases`, `options`, `machine` and `os_user`, and `failure` moves to every pass. Each pass's table rows are fixed. Only the coordinator writes the run log, and a nested run writes into its parent's. Component IH_Log is dropped.
- [Keys that contain @](issues/14-keys-that-contain-at.md): an Alpha or Text record key that contains `@` isn't supported, because 4D reads `@` in a right operand as a wildcard and has no escape. The gate doesn't look for one. The export refuses (`refused`) when it encodes one, and the health check scan lists them as blockers. A table whose cut key contains `@` runs as one job. Compare reports a target key with `@` as extra on sight, and the fixer never looks a key up with `QUERY` `=`. [Facts](research/14-at-wildcard-4d-facts.md)
- [Worker count and contention between workers](issues/15-worker-count-and-contention.md): preemptive workers contend inside 4D, so `workers` defaults to a constant per pass, capped at the core count: 2 for Compare and 4 for the others, from the evidence so far, with no measurement. One number covers every phase of a pass, `0` in the shared methods means the default, and the dialog has a pre-filled field per step. The cut rule stands, and the bench runs once at the defaults. Reworking the codec waits on [Probe: the codec without object operations](issues/17-probe-codec-without-object-operations.md). [Facts](research/15-preemptive-contention-4d-facts.md)
- [Extras before an order guard break](issues/16-extras-before-an-order-break.md): once a table's order guard breaks, every extra of that table, in all its jobs, becomes unverified, except keys that contain `@`. Missing, changed and duplicate stand, the verdict rules don't change, and the run report adds nothing. Built in [Compare: extras before an order guard break](../../exact-copy-v2-build/issues/22-compare-extras-before-an-order-break.md).
- [Probe: the codec without object operations](issues/17-probe-codec-without-object-operations.md): an encode from descriptor arrays is 11 to 23% faster than `_Codec.encode()` at every worker count, but neither collapses: the total rises to 3.3 times one worker's at 10 workers. Ticket 09's 30-times slowdown lies elsewhere in Compare's per-record path, likely in the objects it creates per record (an inference). [Results](research/17-__Spike_Codec_Cost-compiled.json)
- [Rework the codec's per-record loops](issues/18-rework-codec-per-record-loops.md): no rework of the codec: arrays save 11 to 23% of `encode()`, a small share of a pass. On the bench, Compare's cost a record grows 35 times from 1 worker to 10 and the export's 7.7, so the collapse is in what `_CompareJob` adds per record. A probe isolates it first: [Probe: Compare's per-record path](issues/20-probe-compare-per-record-path.md), then [Rework Compare's per-record path](issues/21-rework-compare-per-record-path.md). The `workers` defaults don't change, and `SELECTION RANGE TO ARRAY` is dropped.

## Out of scope

- **Reading old XML exports or old MD5 files:** each migration uses a single component version from start to finish.
- **Securing or encrypting the export set:** protecting the folder is the operator's responsibility.
- **Building the new version:** it follows this map, as separate build tickets.
- **Supporting text record keys that contain `@`:** the export refuses them ([Keys that contain @](issues/14-keys-that-contain-at.md)). Support would need a key comparison without wildcards that orders like the index (`Compare strings` is the candidate) and cut keys without `@`.
